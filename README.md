# Ответы на отзывы в App Store и Google Play

ИИ пишет черновики ответов на отзывы, человек их подтверждает, сервис
публикует. Параллельно поток негатива превращается в агрегаты по версиям,
темам и локалям — это и есть основная польза, ответы сами по себе лишь гигиена.

**Ни один ответ не уходит в магазин без подтверждения человеком.**

## Как устроено

Магазины не дают вебхуков — только опрос. Поэтому конвейер собран как
цепочка шагов, разделённых состоянием в БД: сбой генерации никогда не
приводит к публикации мусора, а сбой публикации не требует перегенерации.

```
cron
 ├─ ingest   App Store Connect API + Google Play Developer API → reviews
 ├─ analyze  LLM, структурированный вывод → review_analysis + review_topics
 ├─ draft    LLM → replies (status=pending)
 ├─ (человек) админка: подтвердить / поправить / отклонить → approved
 └─ publish  отправка в магазины, ретраи, фиксация published_at
```

| Модуль | Что делает |
|---|---|
| `app/stores/` | адаптеры магазинов: `appstore.py`, `googleplay.py`, `mock.py` |
| `app/llm/` | схемы структурированного вывода, версионированные промпты, профиль бренда |
| `app/pipeline/` | шаги конвейера: ingest, analyze, draft, publish, digest |
| `app/moderation.py` | действия модератора и очередь |
| `app/analytics.py` | агрегаты по отзывам |
| `app/alerts.py` | правила алертов (обычный SQL, без LLM) |
| `app/web/` | HTTP API и страница модерации |

## Быстрый старт (без единого реального ключа)

Мок-адаптеры читают отзывы из `fixtures/` и складывают «опубликованные»
ответы в `.runtime/` — весь конвейер гоняется локально.

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

cp .env.example .env          # STORE_MODE=mock уже стоит по умолчанию
cp brand.example.json brand.json
export ANTHROPIC_API_KEY=sk-ant-...

reviews init-db
reviews cycle                 # сбор → анализ → черновики → публикация
reviews serve                 # админка на http://127.0.0.1:8000
```

В админке: очередь отсортирована по серьёзности, `A` — подтвердить,
`R` — отклонить, счётчик символов показывает лимит площадки. Вкладка
«Аналитика» — дашборд, алерты и качество генерации.

Тесты (сеть и ключи не нужны — модель подменена):

```bash
pytest
```

## Подключение боевых магазинов

В `.env` поставьте `STORE_MODE=real` и заполните доступы.

**App Store Connect.** Ключ создаётся в App Store Connect → Users and
Access → Integrations; нужны Issuer ID, Key ID и файл `.p8`. Авторизация —
JWT на ES256, токен пересоздаётся автоматически.

`APPSTORE_TERRITORIES` — список территорий через запятую. Пусто = один
общий проход. Если видите, что отзывы из части стран не доходят,
перечислите территории явно: выдача идёт по территориям, и без перебора
часть отзывов не попадает в первые страницы.

**Google Play.** Сервисный аккаунт, привязанный в Play Console → Users
and permissions, JSON-ключ и `GOOGLEPLAY_PACKAGE_NAME`.

> **Важное ограничение Google Play.** `reviews.list` отдаёт только отзывы
> за последние ~7 дней и только те, где есть текст. Если воркер не
> отработал неделю — эти отзывы потеряны навсегда, догрузить их неоткуда.
> Поэтому в `app/alerts.py` есть правило на молчащий сбор: предупреждение
> через 24 часа, критический алерт через 96.

Публикация включается отдельным рубильником: `PUBLISH_ENABLED=true`.
Пока он выключен, конвейер работает полностью, но в магазины ничего не
уходит — удобно и для первого запуска, и как аварийный стоп.

## Лимиты площадок

| | Лимит ответа | Особенности |
|---|---|---|
| App Store | 5970 символов | повторный POST заменяет ответ; ответ можно удалить |
| Google Play | **350 символов** | один ответ на отзыв, повторный вызов перезаписывает |

350 против 5970 — это разные жанры письма, поэтому текст генерируется
отдельно под каждую площадку, с запасом в 15% от лимита. Длина
проверяется кодом (в генераторе, в модерации и в адаптере), а не доверием
к модели.

## Что уходит к человеку без черновика

Черновик не генерируется вообще, если анализ поставил:

- любой `risk_flag` — угроза суда, сообщение об уязвимости, заявление о
  нарушении правил магазина, упоминание прессы;
- `severity >= DRAFT_SEVERITY_CEILING` (по умолчанию 4 — потеря денег или
  данных).

Такие карточки попадают в очередь со статусом `needs_human` и пустым
полем ответа. Модель, которая бойко отвечает на юридическую угрозу, —
источник проблем, а не экономии.

## Стоимость

Анализ — самый массовый вызов, поэтому он идёт дешёвой моделью и, при
желании, через Batch API (вдвое дешевле, результат асинхронный):

```bash
reviews analyze --batch-submit    # отправить пачку
reviews analyze --batch-collect   # забрать результаты следующим тиком
reviews cycle --batch             # то же внутри полного цикла
```

Системный промпт (инструкция + описание продукта) одинаков для всех
отзывов и помечен `cache_control` — переменная часть идёт после точки
кэширования. Модели по умолчанию: анализ — Haiku 4.5, черновики —
Sonnet 5, недельная сводка — Opus 5. Меняются в `.env`.

## Аналитика негатива

```bash
reviews stats     # дашборд: доли негатива, разрезы по версиям и локалям, темы
reviews alerts    # правила: всплеск негатива, кластер темы на версии, риски, свежесть сбора
reviews digest    # недельная сводка от LLM: 5-7 сгруппированных проблем с цитатами
```

Темы — закрытый enum (`app/llm/schemas.py`), а не свободные строки: иначе
агрегаты рассыпаются на синонимы. Разрез по версии приложения — самый
ценный сигнал: скачок негатива сразу после релиза виден раньше, чем в
крашлитиках.

## Как улучшать качество ответов

1. `brand.json` влияет сильнее всего — тон, глоссарий функций, запреты и
   3-5 примеров хороших ответов.
2. `reviews stats` показывает долю черновиков, ушедших в публикацию без
   правок. Падает — промпт разошёлся с реальностью.
3. Топ причин отклонения (вкладка «Аналитика») — готовый список того, что
   чинить в промпте.
4. `reviews examples` выгружает опубликованные ответы: материал для
   few-shot примеров.
5. Меняете промпт — поднимите версию в `app/llm/prompts.py`. Версия
   пишется в каждую строку результата, поэтому видно, что считалось
   по-старому, и можно пересчитать выборочно.

## Что осознанно не сделано

- **Аутентификация в админке.** Сервис рассчитан на закрытый контур: VPN
  или reverse-proxy с авторизацией. Имя модератора приходит заголовком
  `X-Moderator` и пишется в историю решений.
- **Миграции.** `init-db` создаёт схему через `create_all`. Для боевого
  контура подключите alembic.
- **Eval-набор.** Заготовка есть в тестах на подменённой модели, но
  размеченные вручную 100-200 отзывов нужно собрать на своих данных —
  без них правка промпта превращается в гадание.
- **Retention для PII.** Флаг `contains_pii` проставляется, но политику
  хранения и вычистку логов нужно задать под свои требования.
